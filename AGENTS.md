# AGENTS.md — ByteCommander

> Нормативні правила для всіх AI-агентів і людей, які змінюють цей репозиторій.
> Діє з моменту злиття в `main` (ADR-0020). Зміни цього файлу — лише через PR з погодженням власника.
> Якщо правило тут суперечить прямій вказівці власника в задачі, перемагає вказівка власника.

## 1. Що це за проєкт

ByteCommander — двопанельний файловий менеджер для Windows (WPF, .NET 10).
Інтерфейс, коментарі, коміти й PR — українською.

Цільова модель: **модульний моноліт** з напрямком залежностей за Clean Architecture:

```
ByteCommander (WPF, net10.0-windows)  ──►  ByteCommander.Core (net10.0, без WPF і Win32)
  Presentation + Windows-адаптери           Application-модулі + Provider API
```

Повний опис: `docs/architecture/README.md`. Контракти модулів: `docs/architecture/modules.md`.
Матриця залежностей: `docs/architecture/dependency-rules.md`. Рішення: `docs/adr/`.

## 2. Команди

```powershell
dotnet build FileManager.csproj -c Release
dotnet test tests/ByteCommander.Tests -c Release
dotnet test tests/ByteCommander.ArchitectureTests -c Release   # правила залежностей і baseline
dotnet format --verify-no-changes --include <змінені файли>
```

Застосунок і тести, що торкаються WPF, збираються лише на Windows.
`ByteCommander.Core` і `ByteCommander.Core.Tests` (після етапу G3) мають збиратися й на Linux.

## 3. Межі, які не можна порушувати

1. **Жодних циклів** між модулями, просторами імен верхнього рівня й проєктами.
2. **Core не знає про UI і платформу**: у `ByteCommander.Core` заборонені `System.Windows.*`,
   `Microsoft.Win32.*`, P/Invoke (`DllImport`/`LibraryImport`), COM, `Process.Start`, `Application.Current`.
   Платформні можливості — лише через інтерфейси-порти Core, реалізовані в застосунку.
3. **UI не працює з диском напряму**: вікна й контроли не викликають `File`, `Directory`,
   `FileInfo`, `DirectoryInfo`, `DriveInfo`, `FileStream`. Лише через сервіси Core / провайдер.
   Наявні порушення зафіксовані в baseline; нові заборонені.
4. **Жодних тривалих файлових операцій у UI-потоці**. Усе, що може чекати диск або мережу,
   — `async` з `CancellationToken`. `Dispatcher.Invoke` з робочого потоку — лише для діалогу з користувачем.
5. **Жодного прихованого глобального mutable-стану**: нові `static` поля, що змінюються після старту,
   заборонені. Стан — в екземплярах, отриманих через конструктор.
6. **Звертатися до іншого модуля лише через його публічний API** (типи без `Internal` у просторі імен,
   позначені в `modules.md`). `InternalsVisibleTo` — лише для тестових збірок.
7. **Жодних універсальних класів**: клас відповідає за одну підсистему. Не додавайте методи
   в `Util`, `MainWindow`, `FilePanel` — це borg-класи з baseline, вони мають лише зменшуватися.
8. **Не створюйте абстракцію без другого споживача або тесту, якому вона потрібна** (YAGNI).
   Інтерфейс з однією реалізацією допустимий лише як порт Core → платформа або для contract-тестів.

## 4. Куди класти новий код

| Що додаєте | Куди | Чого не робити |
|---|---|---|
| Алгоритм, правило, планувальник, валідатор | `ByteCommander.Core/<Модуль>/` | не в code-behind вікна |
| Нова операція з файлами | `Core/Operations` через рушій операцій | не прямим `File.*` з UI |
| Новий тип джерела файлів (SFTP, архів…) | новий провайдер `IFileProvider` + contract-тести | не `if (remote)` у командах |
| Виклик Win32/COM/Shell | `ByteCommander/Platform/Windows/` + порт у Core, якщо потрібен Core | не в Core |
| Вікно, контрол, діалог | `ByteCommander/<Feature>/` | без доступу до диска |
| Команда з гарячою клавішею | реєстр команд (`CommandRegistry`), стабільний `Id` | не окремим `KeyDown`-обробником |
| Налаштування | модель + міграція `SchemaVersion` (ADR-11) | не ламати старий JSON |

Якщо модуль неочевидний — спитайте власника до написання коду.

## 5. Кожна зміна повинна

1. Належати одному модулю (або явно перелічити, які модулі зачеплено й чому).
2. Використовувати наявні контракти; новий контракт — з обґрунтуванням у PR, суттєвий — через ADR.
3. Не додавати заборонених залежностей (architecture tests зелені, baseline не зростає).
4. Мати тести відповідного рівня: unit для логіки Core; contract — для провайдерів;
   integration з реальною ФС — для операцій; регресійний тест, що падає до виправлення, — для багфіксу.
5. Не погіршувати Linux-збірку Core та не додавати Windows-специфіку в Core.
6. Не ламати зворотну сумісність (settings.json, гарячі клавіші, CLI `--view`/`--diff`, публічний API Core)
   без погодженої міграції.
7. Не дублювати бізнес-логіку: спершу шукайте наявну (`rg`), потім розширюйте її.
8. Мати критерії приймання в описі PR.

## 6. Коли потрібен ADR

Новий модуль або збірка; нова зовнішня залежність (NuGet); зміна контракту `IFileProvider`,
рушія операцій, формату налаштувань чи публічного API Core; зміна матриці залежностей;
відмова від правила з розділу 3. Шаблон: `docs/adr/0000-template.md`.

## 7. Процес

- Гілки: `feature/…`, `fix/…`, `refactor/…`, `test/…`, `docs/…`. Одна логічна зміна — одна гілка.
- Жодних прямих комітів у `main`, жодного force-push у чужі гілки.
- Рефакторинг і зміна поведінки — різні PR. Рефакторинг не змінює поведінку й не видаляє тестів.
- Не створюйте гілок, комітів, PR, issues, не змінюйте GitHub Settings і не додавайте NuGet-пакетів
  без явного дозволу власника в поточній задачі.
- Не вимикайте, не пропускайте й не видаляйте тести, щоб отримати зелений CI.
- **Жодної AI-атрибуції** ніде в репозиторії та на GitHub: ні в комітах (`Co-Authored-By`, `Claude-Session`,
  «Generated with …»), ні в описах PR, issues, коментарях, коді, документації чи release notes.
  Особливо заборонені посилання на чати, сесії чи артефакти AI-інструментів. Автор змін — власник репозиторію.
- Не редагуйте файли baseline (`build/architecture-baseline.txt`, `build/analyzers-baseline.json`)
  інакше як для **видалення** виправлених записів (виняток — разова звірка з першим прогоном CI, крок G0b).

## 8. Definition of Done

Погоджені вимоги реалізовано · CI зелений, включно з architecture gates ·
нові й наявні тести проходять · baseline не зріс · документація (README, `modules.md`, ADR, CHANGELOG)
оновлена · зворотну сумісність налаштувань перевірено · є план відкату · власник погодив результат.

## 9. Звіти й твердження

Кожне твердження в аналізі чи описі PR позначайте:
`CONFIRMED` (перевірено в коді), `TESTED` (підтверджено тестом), `DOCUMENTED` (документація/API),
`INFERRED` (висновок), `PROPOSED` (пропозиція), `UNKNOWN`.
