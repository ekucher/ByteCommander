# ADR-0013. Modular Monolith і межі модулів

- Статус: Proposed
- Дата: 2026-11-21
- Зачіпає модулі: усі   Змінює ADR: уточнює «Логічні рівні» цільової архітектури (частина 2)

## Контекст
Зараз весь код — один WPF-проєкт `FileManager.csproj` (≈7 600 рядків C#, 30 файлів). Межі між «Services»,
«Dialogs», «Controls» існують лише як папки: граф залежностей файлів має сильно зв'язаний компонент із 8 файлів
(`MainWindow`, `FilePanel`, `Dialogs`, `OperationRunner`, `SearchWindow`, `ViewerWindow`, обидва вікна порівняння),
сервіс `OperationRunner` залежить від `ProgressWindow`, `SearchWindow` — від конкретного `MainWindow`.
Компілятор не може перевірити жодної межі. Тести посилаються на exe застосунку через `InternalsVisibleTo`.

## Розглянуті альтернативи
| Варіант | Плюси | Мінуси |
|---|---|---|
| A. Лишити один проєкт, межі — лише папки | нуль витрат | межі не перевіряються, борг росте |
| B. Проєкт на кожен модуль (≈10 збірок) | компілятор перевіряє все | надмірно для 7 600 рядків; повільніша збірка; багато `public` |
| C. Дві збірки (Core net10.0 + WPF-застосунок), модулі — простори імен у Core, межі перевіряються architecture tests | компілятор гарантує головну межу UI/логіка; решту — тести; мало церемоній | правила між модулями Core тримаються тестами, а не компілятором |
| D. Мікросервіси / окремі процеси | — | не відповідає desktop-застосунку |

## Рішення
C. `ByteCommander.Core` (net10.0, без WPF) і `ByteCommander` (WPF). Модуль Core = простір імен
`ByteCommander.Core.<Модуль>` з публічним API і `Internal`-підпростором. Новий проєкт створюється лише за ADR,
коли межу треба гарантувати компілятором або з'являється другий споживач (CLI, Plugin SDK, `Platform.Windows`
для CLI).

## Наслідки
- `dependency-rules.md` і `modules.md` стають нормативними; architecture tests (ADR-14) — блокуючими після G3.
- Тести діляться: `Core.Tests` (net10.0) і `Tests` (застосунок).
- Узгоджено з частиною 2: «лише дві нові збірки на першому етапі».

## Ризики
| Ризик | Імовірність | Вплив | Пом'якшення |
|---|---|---|---|
| Великий PR переносу файлів | середня | середній | перенос після G1–G2 (цикли вже розірвано), окремий PR без змін логіки |
| Розростання `public` у Core | середня | низький | `internal` за замовчуванням, PublicApiAnalyzers (ADR-19) |

## План міграції
G1 (розрив циклів у межах одного проєкту) → G2 (виділення логіки в папку `Core/` того ж проєкту) →
G3 (створення проєкту Core і перенос папки). Кожен крок — окремий PR, поведінка не змінюється, 102 наявні тести зелені.

## Перевірка
Architecture tests: Core не посилається на WPF/Win32; немає циклів між модулями; Core збирається на ubuntu-latest.
