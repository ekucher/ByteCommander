# ADR-0016. Модель помилок, асинхронності й скасування

- Статус: Proposed
- Дата: 2026-11-21
- Зачіпає: усі модулі Core   Пов'язано: ADR-0012 (журнал)

## Контекст
88 блоків `catch`, з них 9 порожніх; необроблені винятки UI поглинаються; 11 `async void` (зокрема не обробник
`MainWindow.Delete`); 12 ад-хок `Task.Run` з різною обробкою помилок; навігація синхронна в UI-потоці.

## Розглянуті альтернативи
| Варіант | Плюси | Мінуси |
|---|---|---|
| A. `Result<T>` усюди | явні помилки | чужорідно для .NET I/O, багато шаблонного коду |
| B. Лише `IOException` | без нових типів | неможливо відрізнити «немає можливості» від «доступ заборонено» |
| C. `FileProviderException(FileErrorCode)` для фатальних, `ItemError`/`OperationResult` для пакетних, `OperationCanceledException` для скасування | відповідає BCL і наявному `FileOperation.Errors` | перехідний період із двома моделями |

## Рішення
C. Усі I/O-методи Core — async з `CancellationToken` останнім параметром; без `.Wait()`/`.Result`;
прогрес через `IProgress<T>`; запит до користувача — через переданий інтерфейс (`IConflictResolver`), Core не викликає `Dispatcher`.
Порожній `catch` дозволено лише з коментарем «чому безпечно»; перехоплене логуються.

## Наслідки
Контракти в `docs/architecture/modules.md`; правила CA2016 і BannedApi (`Task.Wait`, `Task<T>.Result`) у Core.

## Ризики
| Ризик | Імовірність | Вплив | Пом'якшення |
|---|---|---|---|
| Регресії фокусу/порядку подій при переході на async | середня | середній | прапорець `Features.AsyncNavigation` (G4) |

## План міграції
G2 (нові класи пишуться за моделлю), G4 (навігація), G5 (провайдер).

## Перевірка
AR-12 (порожні catch), аналізатори, unit-тести скасування й таймаутів.
